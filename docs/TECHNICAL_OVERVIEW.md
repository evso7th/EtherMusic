# EtherMusic: Технический обзор проекта

## 1. Концепция и архитектура

**EtherMusic** — это веб-приложение, созданное как "нейро-медитативный звуковой процессор". Цель проекта — предоставить пользователю интуитивный инструмент для создания эмбиент-музыки и медитативных звуковых ландшафтов без необходимости в музыкальном образовании.

Приложение построено на современном технологическом стеке, обеспечивающем высокую производительность, интерактивность и качественный звук в браузере.

### Технологический стек:

*   **Фреймворк:** Next.js (React) с App Router.
*   **UI:** ShadCN UI (компоненты на базе Radix UI) и Tailwind CSS для стилизации.
*   **Звуковой движок:** Web Audio API с кастомными AudioWorklet-процессорами.
*   **Язык:** TypeScript для строгой типизации и улучшения качества кода.

## 2. Эволюция звукового движка: Отказ от `Tone.js` в пользу Ворклетов

Архитектура звукового движка — это сердце приложения. Она прошла несколько этапов эволюции в борьбе за производительность и чистоту звука, особенно на мобильных устройствах. Этот путь является ключевым для понимания текущей структуры кода.

### Акт 1: Иллюзия простоты и ловушка `Tone.PolySynth`

**Проблема:** Изначально для обработки полифонической игры использовался `Tone.PolySynth`. Это высокоуровневая абстракция, которая удобна для быстрого прототипирования, но имеет существенные недостатки в реальных условиях:
*   **Накладные расходы:** Создает значительную нагрузку на процессор.
*   **Артефакты звука ("Хрип"):** На мобильных устройствах или при интенсивной игре это приводило к главному врагу любого аудио-приложения — щелчкам, хрипам и задержкам звука.

### Акт 2: Новый враг — Тирания Главного Потока

**Проблема:** Несмотря на оптимизацию синтеза, появился новый враг — **"фризы" интерфейса**. Когда мы вынесли генерацию музыки для **Автопилота** в отдельный Web Worker, основному потоку все еще приходилось управлять сложными объектами `Tone.js`, что приводило к "замораживанию" UI.

**Вывод:** Любые ресурсоемкие операции, включая сложное управление аудио-графом, должны быть вынесены из основного потока.

### Акт 3: Финальное решение — Нативные Ворклеты и Отделение Автопилота

**Архитектурное решение:** Мы полностью отказались от `Tone.js` для синтеза в реальном времени и перешли на архитектуру с кастомными **AudioWorklet-процессорами**.

**Как это работает:**
1.  **Разделение ответственности:**
    *   **Основной поток (`page.tsx` + `AudioEngine.ts`):** Отвечает только за UI и отправку *простых команд* в аудио-ворклеты (например, "noteOn, id, frequency, volume"). Он больше не управляет сложными объектами `Tone.js`.
    *   **Audio Worklets (`public/workers/*.js`):** Легковесные процессоры, работающие в высокоприоритетном аудио-потоке. Они получают команды и самостоятельно генерируют аудио-сэмплы. Это архитектурно решает проблему "хрипов" и "фризов".
2.  **Отделение Автопилота:** Функция Автопилота была настолько сложной, что мы вынесли ее в отдельное приложение — **AuraGroove**. Это позволило EtherMusic сфокусироваться на идеальном ручном и ритмическом исполнении.

**Результат:** Эта архитектура полностью решила проблемы с производительностью. Интерфейс остается на 100% отзывчивым. Это стабильная и масштабируемая модель.

## 3. Обзор ключевых модулей

*   **`AudioEngine.ts`:** "Сердце" приложения. Управляет `AudioContext`, всеми нодами (Gain, Compressor, Convolver) и ворклетами. Передает команды от UI в ворклеты. Управляет записью сессии.
*   **`drum-machine.ts`:** Отвечает за ритм-секцию. Вместо `Tone.Part` использует собственный планировщик на `setTimeout` для большей гибкости и контроля над свингом и сбивками, отправляя команды в `drum-processor.js`.
*   **`synth-processor.js` и `drum-processor.js`:** AudioWorklet-процессоры, отвечающие за генерацию звука синтезаторов и воспроизведение сэмплов ударных.
*   **`page.tsx`:** Главный React-компонент. Является "единым источником правды" (Single Source of Truth) для всего состояния UI. Он передает команды в `AudioEngine` через хук `useAudioEngine`.
*   **`LatchEngine.ts`:** Управляет логикой "удержания" нот на басовом пэде.

## 4. Сценарии использования

*   **Полностью ручная игра:** Пользователь играет на обоих термен-пэдах, используя Latch-режим для удержания басовых нот.
*   **Игра с ритм-секцией:** Пользователь включает один из паттернов ударных и импровизирует под него.

## 5. Новые возможности (v2.1)

*   **Свинг и сбивки:** Ритм-секция стала более живой за счет добавления свинга и автоматических сбивок.
*   **Полный отказ от Tone.js для синтеза:** Переход на нативные AudioWorklet'ы для максимальной производительности.
*   **Улучшенные пресеты:** Переработаны пресеты инструментов для более качественного и разнообразного звучания.
